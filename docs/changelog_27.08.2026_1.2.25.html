2. Доступ к Telegram и Web API

Telegram-бот

  • ADDEDBotAccessMiddleware проверяет ID отправителя до передачи сообщения обработчикам. Неавторизованные пользователи не получают доступ к операциям с зарплатой.
  • Разрешённые ID читаются из SALARYAPP_BOT_ALLOWED_IDS или BOT_ALLOWED_IDS: переменные окружения имеют приоритет над bot/.env. Поддерживается несколько положительных ID через запятую или точку с запятой.
  • При пустом или некорректном списке бот не запускается. Проверка доступа выполняется до подключения к Telegram.
  • Загрузка токена, прокси и allowlist собрана в bot/config.py. Старый неиспользуемый bot/bot_config.py с шаблонными значениями удалён.
  • В bot/.env.example добавлен пример обязательного списка разрешённых ID. Настоящие токены и персональные ID в релиз не включаются.

Web API

  • FIXEDАвторизация установлена централизованно через before_request для всех маршрутов /api/, включая чтение данных, настройки, экспорт и операции с резервными копиями.
  • Внешний запрос требует непустого настроенного API-ключа и заголовка X-API-Key. Сравнение выполняется через hmac.compare_digest.
  • Передача ключа в query string больше не поддерживается. Это исключает данный способ попадания ключа в адресную строку и историю URL.
  • Для прямых обращений с 127.0.0.1 и ::1 сохранён доступ без ключа. По умолчанию сервер слушает только loopback.

Граница защиты: исключение для loopback рассчитано на прямой локальный запуск. Если перед приложением ставится локальный reverse proxy, схему авторизации нужно отдельно пересмотреть. Передача API-ключа по внешней сети также требует защищённого транспорта; этот релиз не настраивает HTTPS.

3. Деньги и целостность SQLite

  • MIGRATIONДобавлена 005_salary_integrity. В таблице salaries суммы аванса и зарплаты переводятся из рублей REAL в целые копейки INTEGER.
  • Схема ограничивает год диапазоном 2000-2100, месяц диапазоном 1-12, суммы неотрицательными значениями; комбинация года и месяца уникальна.
  • Перед перестройкой непустой таблицы автоматически создаётся архив резервной копии. Ошибка создания бэкапа прерывает миграцию до изменения таблицы.
  • Проверки некорректных строк и повторяющихся периодов останавливают миграцию. Дубликаты не объединяются и не удаляются автоматически.
  • Каждая миграция выполняется в транзакции с записью её имени после успешного изменения схемы; при исключении выполняется rollback транзакции.
  • SalaryRepository.upsert() использует INSERT ... ON CONFLICT ... DO UPDATE ... RETURNING. Параллельная запись одного периода не создаёт несколько строк.
  • Публичные модели и API по-прежнему возвращают рубли. Агрегаты, экспорт и статистика учитывают новое внутреннее представление сумм.
  • В money_values.py добавлены Decimal-нормализация и преобразование в копейки. Отклоняются отрицательные суммы, NaN, бесконечность и значения выше установленного предела; округление до двух знаков выполняется по ROUND_HALF_UP.
  • Соединения остаются thread-local; включены WAL, внешние ключи, busy timeout и synchronous=NORMAL. Web-запрос закрывает своё соединение при завершении контекста.

Проверка совместимости: миграция выполнена на отдельном SQLite-снимке dev-БД. Сумма до и после преобразования совпала до копейки, тип хранения стал INTEGER. Персональные суммы и содержимое БД в отчёт не включены.

4. Резервные копии и восстановление

  • BACKUPВместо прямого архивирования открытого файла используется согласованный снимок через SQLite Backup API, включая данные, находящиеся в WAL.
  • Снимок проверяется через PRAGMA quick_check и наличие таблицы salaries. Проверяются ненулевой размер и верхний предел 2 ГиБ.
  • Архив сначала записывается во временный файл, затем публикуется через os.replace. Микросекунды в имени уменьшают риск совпадения имён.
  • Операции восстановления и удаления ограничены каталогом резервных копий, расширением ZIP и префиксом salary_backup_.
  • Для восстановления требуется ровно один DB-файл в корне архива. Извлечение выполняется в заданный временный файл, без extractall; вложенные пути отклоняются.
  • Перед восстановлением создаётся копия текущей БД. Затем применяется SQLite Backup API, закрывается текущее соединение и запускаются миграции восстановленной базы.
  • Метаданные ограничены по размеру; комментарии при создании нормализуются. Список резервных копий содержит необходимые desktop-поля и ISO-даты для Web.

Добавлены тесты восстановления изменённых данных, метаданных, запрета удаления за пределами backup-каталога и отказа от DB-файла во вложенном пути архива.

5. Защита ручного deploy

  • FIXEDОтсутствующий или пустой список исключений останавливает процесс до очистки production. Ошибка проверки исключения приводит к пропуску элемента.
  • Результат создания копии production проверяется. При неполном бэкапе обновление не продолжается, в том числе с --yes.
  • Ошибка чтения защищаемого bot/.env прерывает deploy до очистки. Ошибки восстановления защищённых файлов также считаются ошибками обновления.
  • Добавлен rollback_from_backup(): при ошибках очистки, копирования, записи версии или итоговой проверки предпринимается восстановление предыдущего кода из преддеплойного бэкапа.
  • Сохранены проверки направления dev → production через prod.marker и запрет совпадения источника и цели.
  • Итоговая проверка включает все пять обязательных точек входа, конфигурацию, маркер, зависимости и production-файл bot/.env.

Важно: deploy обновляет код, а не рабочую БД. Автоматический rollback deploy не является откатом миграции SQLite и не заменяет резервную копию данных. Если восстановление кода само завершится ошибкой, потребуется ручное восстановление из сохранённого каталога бэкапа.

6. Разделение ответственности слоёв

Настройки

  • SettingsService отвечает за поддерживаемые ключи, значения по умолчанию, диапазоны и нормализацию настроек. API больше не работает с репозиторием настроек напрямую.
  • SettingsRepository.set_settings() сохраняет пакет в транзакции. Валидация всего пакета происходит до записи; ошибочный параметр не приводит к частичному сохранению.
  • Контроллер настроек проверяет результат API и не показывает сообщение об успехе при отказе.
  • MainView.apply_settings() получает подготовленные значения от контроллера. Прямые чтения SettingsRepository из View удалены.
  • Валюта передаётся через контроллер и presenter в KPI. Утилита форматирования денег больше не читает настройки из БД.
  • Для новых установок срок хранения резервных копий унифицирован на 30 дней. Уже сохранённые пользовательские значения не переписываются.

Аналитика, экспорт и Telegram

  • AnalyticsRepository содержит SQL годовых итогов, средних значений, лучших периодов и общей статистики. Сервисы статистики и экспорта используют репозиторный слой.
  • Общее правило среднемесячного дохода перенесено в функцию модели года. YearSummary больше не импортирует StatisticsService; сам сервис использует ту же функцию.
  • CSV и Excel формируются из моделей и агрегатов репозитория, без прямых SQL-запросов в ExportService.
  • Восстановление и удаление копий в desktop выполняются через SalaryAPI. Добавлен фасад получения текущего периода.
  • Команды и FSM бота находятся в bot/handlers/salary.py, состояния используют aiogram v3. bot/main.py отвечает за логирование, конфигурацию, сборку dispatcher и запуск polling.

Изменения устраняют найденные нарушения границ слоёв и дублирование. Это не утверждение о формальном полном соответствии всего репозитория всем принципам SOLID: исторический код и оставшиеся ограничения требуют отдельного контроля при дальнейших изменениях.

7. Web, запуск и обработка ошибок

  • SERVERОбычный запуск Web выполняется через Waitress с четырьмя потоками. Flask development-сервер используется только при явно включённом debug.
  • Добавлены API для восстановления и удаления резервной копии. Web-заглушка восстановления заменена запросом к серверу, добавлена кнопка удаления с подтверждением.
  • Имена файлов и комментарии экранируются при построении HTML списка копий. Кнопки имеют подсказки действия.
  • Для API-ошибок 404 и 500 возвращается JSON, а не HTML-страница. Исключения на границах API логируются; ошибки приложения включены в список обрабатываемых исключений.
  • Пути БД, резервных копий и экспорта разрешаются относительно корня проекта, а не текущей рабочей папки процесса.
  • run_web.bat переведён из CP1251 в UTF-8, использует кодовую страницу 65001 и проверяет Waitress. При отсутствии зависимостей показывает команду установки, а не выполняет устаревшую установку пакетов.
  • В run_bot.bat путь рабочей папки заключён в кавычки, установка зависимостей вызывается через python -m pip.
  • Логирование бота настраивается при запуске, а не при импорте модуля.

11. Обновление production и ограничения отката

  1. Остановить desktop, Web и Telegram-бота, работающих с production-БД. Не оставлять процессы старой версии активными во время изменения схемы.
  2. Убедиться в наличии актуальной резервной копии рабочей БД и проверить production-файл bot/.env. Если BOT_ALLOWED_IDS уже содержит правильный числовой ID, менять его не нужно.
  3. Запустить согласованный скрипт deploy из dev-каталога. Маркер production и защищаемый bot/.env сохраняются. Подготовка этого релиза сама по себе production не обновляет.
  4. В Python-окружении production установить зависимости из нового requirements.txt через python -m pip install -r requirements.txt.
  5. Первый запуск выполнить для одного интерфейса. Для непустой БД перед 005 будет создана автоматическая копия; при конфликтных данных или ошибке бэкапа запуск миграции остановится.
  6. Проверить историю и суммы, экспорт, резервные копии, Web и Telegram. После этого запускать остальные интерфейсы и автозапуск.
# Пример настройки доступа, без реальных идентификаторов
BOT_ALLOWED_IDS=123456789

# Установка runtime-зависимостей в окружении production
python -m pip install -r requirements.txt

Обратная совместимость БД: после 005 старый код интерпретирует копейки как рубли. Простого возврата файлов версии 1.2.24 недостаточно. Для downgrade необходимо остановить все интерфейсы и согласованно восстановить старый код и домиграционную SQLite-БД. Встроенное восстановление новой версии снова применяет актуальные миграции, поэтому не является инструментом downgrade. Домиграционную копию следует сохранить отдельно до окончания проверки обновления.

Автоматическая резервная копия перед восстановлением сохраняет исходные данные, но не отменяет необходимость ручного восстановления при непредвиденном сбое. Не запускать восстановление параллельно с записью данных из других интерфейсов.
