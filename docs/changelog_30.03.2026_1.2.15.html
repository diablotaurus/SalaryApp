Проблема и причина

Проблема: на Windows Git выдавал предупреждения вида LF will be replaced by CRLF, потому что в проекте не было явных репозиторных правил для переводов строк, а локальная настройка core.autocrlf=true вносила собственное поведение в рабочую копию.
До изменений
  • В проекте отсутствовал .gitattributes.
  • В проекте отсутствовал .editorconfig.
  • Git опирался на локальную Windows-настройку и местами конвертировал строки в CRLF.
  • Редакторы не имели единой инструкции по UTF-8 и окончаниям строк.
После изменений
  • Добавлен .gitattributes с явными правилами по типам файлов.
  • Добавлен .editorconfig для UTF-8, LF и базовой гигиены файлов.
  • *.py, *.html, *.js, *.css, *.md, *.txt и другие текстовые файлы закреплены за LF.
  • *.bat и *.url оставлены в CRLF, что безопасно для Windows.

Что именно добавлено

ДОБАВЛЕН .gitattributes
  • Включено общее правило * text=auto.
  • Для исходников и документации зафиксирован eol=lf.
  • Для Windows-специфичных файлов *.bat и *.url оставлен eol=crlf.
  • Файл salary_icon.ico объявлен бинарным.
ДОБАВЛЕН .editorconfig
  • Установлен charset = utf-8.
  • Для большинства файлов задан end_of_line = lf.
  • Включены insert_final_newline = true и trim_trailing_whitespace = true.
  • Для *.bat и *.url отдельно задан crlf.
Результат: теперь правила формата файлов описаны прямо в репозитории, а не зависят от того, на какой машине и с какими глобальными git-настройками работает разработчик.

Что показала попытка полной renormalize

Фактический результат

  • Команда git add --renormalize . не дала массовых staged-изменений.
  • Это означает, что в истории Git большая часть текстовых файлов уже хранится в нормализованном виде.
  • Проблема находилась не в коммитах репозитория, а в поведении рабочей копии на Windows.

Почему это важно

  • Не понадобился шумный коммит на десятки файлов только ради замены EOL.
  • Удалось решить проблему инфраструктурно и безопасно.
  • Бизнес-логика, UI и данные проекта не затронуты.

Проверка

  • Выполнен анализ текущего состояния через git ls-files --eol.
  • Проверено, что массовый renormalize не создаёт лишних commit-изменений.
  • Прогнан проектный скрипт scripts/check_encoding.ps1.
  • Локальная настройка репозитория была выровнена под новые правила, чтобы снизить вероятность повторных предупреждений на этой машине.
Важно: часть старых файлов в конкретной рабочей копии может по-прежнему отображаться Git как имеющая Windows-формат строк до их повторного checkout/редактирования, но теперь у проекта есть корректные правила, которые предотвращают расползание этой проблемы дальше.
