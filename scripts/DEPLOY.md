# Деплой SalaryApp в production

Краткая памятка: как перенести изменения из рабочей ветки (**dev**) в **production**.

---

## 📍 Где что находится (пример)

| Что | Путь (пример) |
|---|---|
| Рабочая ветка (dev, репозиторий git) | `<DEV>\SalaryApp\current` |
| Production (рабочая версия) | `<PROD>\SalaryApp` |
| Реальная база данных | `<DATA>\SalaryApp Data\db` |

> Конкретные пути у каждого свои и **не хранятся в репозитории**. Путь к production
> задаётся локально (см. «Настройка» ниже).
>
> ⚠️ В production папка `db` может быть **символической ссылкой (junction)** на каталог
> с реальной БД на другом диске. Скрипт деплоя её **никогда не трогает** (ни копирует, ни удаляет).

---

## ⚙️ Настройка перед первым запуском

Скрипт деплоя должен знать путь к production. Задайте его одним из способов (порядок приоритета):

1. **Аргументом** при запуске:
   ```
   python scripts/deploy_to_prod.py "D:\путь\к\SalaryApp"
   ```
2. **Переменной окружения** `SALARYAPP_PROD_DIR`.
3. **Локальным файлом** `scripts/deploy_target.local.txt` — одна строка с путём.
   Файл в `.gitignore` и не публикуется. Рекомендуется для удобства (двойной клик по `.bat`).

Источник (dev) определяется автоматически как корень репозитория (относительно `scripts/`).

---

## 🚀 Как задеплоить

1. Закрой desktop-приложение SalaryApp из прода, если оно открыто.
2. Закоммить изменения в репозитории (версию в `version.txt` повышай только при подготовке релиза — правила в `AGENTS.md`).
3. Запусти деплой:
   - **Двойной клик** по `scripts\deploy_to_prod.bat`;
   - или из терминала, находясь в корне репозитория:
     ```
     python scripts/deploy_to_prod.py --restart-services
     ```
4. Проверь приложение из прода: в заголовке окна должна быть пометка **«РЕАЛЬНАЯ БАЗА ДАННЫХ»**.

### Перезапуск web и бота (`--restart-services`)

Web-сервер и Telegram-бот работают постоянно (задачи Планировщика `SalaryAppWeb` и `SalaryAppBot`) и держат код в памяти: после деплоя без перезапуска они продолжают выполнять **старый** код, а web при этом берёт уже новые шаблоны и статику с диска.

- С флагом `--restart-services` скрипт после успешного деплоя перезапускает обе задачи и проверяет, что они снова в состоянии `Running`. Отсутствующие и отключённые задачи не трогаются. Если перезапуск не удался, скрипт сообщит об этом и завершится с кодом 1 (код уже обновлён, отката не будет).
- Без флага скрипт только напомнит, какие сервисы работают на старом коде, и покажет команды для ручного перезапуска.
- Вместе с `--dry-run` покажет, какие задачи были бы перезапущены, ничего не трогая.

### Сначала посмотреть, что будет сделано (без изменений)

```
python scripts/deploy_to_prod.py --dry-run
```
`--dry-run` показывает весь план (что удалится, что скопируется, какая версия запишется), **ничего не меняя**. Рекомендуется запускать перед первым реальным деплоем.

---

## 🧩 Что делает скрипт `deploy_to_prod.py`

1. **Проверки безопасности.** Источник должен быть dev-репозиторием (есть `version.txt` и **нет** `prod.marker` — иначе скрипт решит, что запущен из прода, и остановится); цель должна существовать и содержать `prod.marker`; источник и цель не должны совпадать. Эти проверки гарантируют направление «из dev → в prod».
2. **Резервная копия прода** → `prod\.backup\<версия>_<дата_время>\` (без `db`, `.backup`, `prod.marker`, `__pycache__`, `nppBackup`).
3. **Снимок секрета** `prod\bot\.env` (сохраняется в память).
4. **Очистка прода** — удаляется всё, **кроме** сохраняемых элементов (см. ниже).
5. **Копирование** `dev → prod` по списку исключений `deploy_exclude.txt`.
6. **version.txt** — в прод пишется **очищенная** версия без суффикса ` current` (например, `1.2.22`).
7. **Восстановление** `prod\bot\.env` (прод-токен не теряется и не подменяется dev-токеном).
8. **Проверки** ключевых файлов и итоговый отчёт.
9. **Сервисы:** с `--restart-services` — перезапуск `SalaryAppWeb`/`SalaryAppBot`, без флага — напоминание, если они работают на старом коде.

### Что СОХРАНЯЕТСЯ при очистке (не удаляется)
`.backup`, `db` (симлинк), `prod.marker`, `exports`, `logs`, `nppBackup`, а также любые символические ссылки.

### Что НЕ копируется из dev (см. `deploy_exclude.txt`)
База данных и бэкапы (`db`, `*.db`, `*.bak`), `prod.marker`, секреты (`bot/.env`, `*.env`), git-инфраструктура (`.git`, `.gitignore`, `.github`, …), виртуальные окружения (`.venv`), кэш/логи (`__pycache__`, `*.pyc`, `*.log`, `logs/`), `exports/`, тесты (`tests/`, `test_*`), IDE-файлы и т.п.

---

## 🔐 Важно про токен бота

У прода свой `bot\.env` со своим токеном. Скрипт **намеренно**:
- не копирует dev-`bot/.env` в прод (исключение в `deploy_exclude.txt`);
- сохраняет и возвращает прод-`bot/.env` вокруг очистки.

Если меняешь токен бота — правь его **в проде вручную** (`prod\bot\.env`), деплой его не перезапишет.

---

## 💾 Резервное копирование БД (отдельно)

Деплой кода **не делает** бэкап базы. Бэкап БД выполняется отдельным скриптом, который лежит
рядом с данными (вне репозитория), например:

- `<DATA>\SalaryApp Data\.db_scripts\db_backup.py` — архивирует папку БД в `…\.backup\*.zip`.

Рекомендуется делать бэкап БД перед крупными изменениями схемы/миграциями.

## 🗄️ Старые скрипты (legacy)

Ранее деплой выполнялся скриптами в папке данных (их **можно не использовать**, канонический скрипт теперь здесь, в `scripts/`):

- `<DATA>\SalaryApp Data\.do_release\update_prod.py` (+ `update_prod.bat`, `update_exclude.txt`) — прежняя версия деплоя.
- `<DATA>\SalaryApp Data\.db_scripts\.backup\update_prod.py` — устаревшая копия (архив).

Отличия нового скрипта: защита `bot/.env`, очистка суффикса ` current` в `version.txt`, исключение `.git`/`.venv`, сохранение `exports`/`logs` при очистке, режим `--dry-run`, защита «источник ≠ цель» и распознавание запуска из прода по `prod.marker`.
